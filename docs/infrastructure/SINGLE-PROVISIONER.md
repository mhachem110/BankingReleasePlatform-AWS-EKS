Adding an allow is not a remedy for an explicit deny. The provisioning permissions family is split into customer-managed policy documents: each is below 6,144 non-whitespace characters. The [review manifest](../../iam/provisioning/proposed/review-manifest.json) records canonical hashes, sizes and unresolved identifiers. Publish/attach only reviewed finalized stage documents; never attach all templates. Preserve existing policy attachments and check the actual role's attachment/inline-size quotas before an administrator adds anything. The service boundary is attached to the three service roles, **never to the shared bootstrap role**.

There is no unrestricted IAM administration, policy creation/versioning, bootstrap-role editing, boundary removal or IAM PassRole in the IAM prerequisite cap. AttachRolePolicy is conditioned on each exact policy ARN and the fixed service boundary; PutRolePolicy is similarly conditioned on the boundary. AWS cannot constrain an inline policy's JSON or policy name through that permission alone. The fixed boundary blocks IAM/STS administration, and the saved-plan guard checks the exact BankingFlowLogs name and document. AWS-managed service policy versions are collected before the plan and compared again before apply; AWS owns their versions.

The IAM preflight also requires the exact managed IAM grant to be attached to the bootstrap identity, verifies both original inline documents and both original trust statements, and blocks denied/incomplete creation simulations before backend initialization. IAM simulations use its global us-east-1 endpoint context; regional workload APIs stay in Ohio. An allowed simulation remains advisory and does not grant permission.

Routine platform sessions cannot create/attach/change roles or create/administer keys. They use three approved managed session caps plus explicit IAM/key-administration denials, avoiding the 2,048-character STS inline limit. Existing dev data uses its separately pinned Phase6Session cap; the data provisioning grant proposals supplement underlying role permissions without changing its gates. The legacy Phase3 wildcard review template is superseded for the new single-role design.

Important AWS limits are recorded rather than hidden:

- EKS CreateCluster supports no resource-level ARN restriction. Its required Resource * statement is constrained by Ohio, Banking tags/name tag, Kubernetes 1.36, the approved encryption-key set, deletion protection and disabled creator admin/self-managed add-ons. The exact Terraform inventory fixes the actual cluster name. IAM cannot enforce the API name through the Name tag alone.
- EC2's automatically created default security group is initially untagged. Provider 6.68.0 tags it before closing its rules. CreateTags has no ec2:Vpc condition for security-group resources. The proposal uses an exact default-SG identifier placeholder and refuses unresolved apply; it does not authorize tagging arbitrary untagged groups. The new protected network-prerequisites.yml intentionally targets only module.network.aws_vpc.this plus its local prerequisite guard. It obtains the exact VPC/default-group IDs from native platform state and verifies them against live EC2 ownership, tags and group membership. The full platform plan requires NETWORK_SEED_REVIEW_JSON and a reviewed cap naming that exact default group. This initial staged target is confined to seed creation; routine/full platform plans have no target.
- The cluster issuer is generated at creation. The initial OIDC proposal permits only Ohio EKS issuer resources with Banking request tags; Terraform derives the URL from the new cluster, never GitHub. Pin the actual issuer ARN after creation through a separate policy review. No role/trust administration accompanies this permission.
- The AWS EKS system-image registry is an explicit external account exception for image pulls only. The Banking resource account remains 866934333672. Review the exact add-on image inventory at platform acceptance; it is not permission to deploy unrelated resources in that account.
- RDS-generated master-secret IDs are unknown beforehand. The proposal requires RDS-mediated calls and restricts creation/tag/description to rds!db-*; no secret-value read, update or deletion is proposed. Validate this service context with the exact later plan and administrator review.

Retaining both Banking and Retail trust on **one** role means both protected bootstrap trust paths ultimately assume the same underlying identity grants. A role policy cannot generally distinguish GitHub repositories after assumption without additional trusted identity context. This design adds no OIDC subjects, but an administrator must review the Retail bootstrap workflow/session restrictions too before approving new Banking grants on the shared identity.
